# Implementation Worklog

This file records product decisions and the evidence behind them. Keep it short, factual, and current. Update it after schema, renderer, timeline, layer, export, performance, or acceptance decisions.

## Status

Mode: product

Binary Halftone renders a procedural 3D scene or an uploaded image as a grid of glyphs. This is a reference-runtime-clone migration of the pre-existing framework-free `binary-halftone` engine (repo root) into this Toolcraft app. The acceptance-row matrix (Decision Trail Iteration 2) is complete: every visible product control has a real, live-tested acceptance row, and the `appTransferMode.referenceFeatureInventory` bundle is reconciled to real evidence. Four known items remain open by deliberate choice or pre-existing environment limitation; see Risks.

## Decision Trail

### Iteration 1 - Type the engine, build schema/canvasContent/rendererPipeline

- Request: Migrate the existing ASCII-halftone renderer into Toolcraft. Type `src/app/halftone.ts` (the framework-free engine, copied in as-is) without changing its algorithm, then build the schema, canvasContent renderer, and a typed rendererPipeline around it. Move all app code that was previously hand-rolled (media upload, image/video export, persistence, preset transfer, canvas sizing/background/render scale) onto Toolcraft runtime surfaces instead of reimplementing it. Keep cellWidth/cellAspect as product controls and derive columns/rows from the runtime canvas size; drop autoFit/fitGridToMedia. Video-as-source was explicitly scoped out of this pass (user decision) in favor of scene + image sources.
- Task type: Reference-app port; schema, renderer, and performance authoring.
- User-visible result: The app shows a procedural raymarched scene by default, switches to a silhouette-inflate or bitmap-luminance render when an image is uploaded, and exposes Source/Placement/Silhouette/Character/Grid/Tone/Light/Ink/Background/Image Export controls plus sticky Export PNG and Copy Tokens actions.
- Source/reference checked: Repo root `App.jsx`, `src/halftone.js` (now `src/app/halftone.ts`), `video.js`, `README.md`.
- Reference inputs: The pre-migration DialKit build at the repository root (App.jsx / halftone.js / video.js / presets.js / README.md), used purely as source code to read, not as a moving-image/design reference; no Figma file was supplied for this pass. presets.js had already been removed before this pass began.

- Decision: Keep `src/app/halftone.ts` byte-for-byte algorithmically identical to the reference engine, only adding TypeScript types (`Field`, `Tokens`, `Ramp`/`RampPool`/`RampCombo`, `PlaceOptions`, `SceneOptions`, `InflateOptions`, `KeyField`, `HalftoneSourceMedia`, `CanvasFactory`). Product code (`halftone-tokens.ts`, `halftone-field.ts`, `halftone-render.ts`, `halftone-canvas.tsx`, `halftone-export.ts`, `halftone-media.ts`) wraps the engine to read runtime state instead of DialKit dial values, without touching engine internals. `canvasContent` is a single React component (`HalftoneCanvas`) that reads `useToolcraft()` state and redraws on every state change; PNG export renders the same unmodified engine output into an offscreen canvas at `pixelRatio` and composites it into `createToolcraftPngExportCanvas`'s prepared context.
- Alternatives rejected: Rewriting the renderer to update `drawHalftone` in place to accept an externally-owned context (rejected: would touch the reference engine's function signature/side effects for no behavioral gain, and the offscreen-canvas + `drawImage` composite achieves the same result with zero engine changes). Rewriting the halftone technique in WebGL/WebGPU (rejected: the reference algorithm is Canvas 2D `ctx.font`/`ctx.fillText` glyph drawing, not a per-pixel filter; the user explicitly asked to keep the algorithm as-is).
- State/output mapping: Schema controls write to `state.values` under dot-namespaced targets (`source.*`, `placement.*`, `silhouette.*`, `character.*`, `grid.*`, `tone.*`, `light.*`, `appearance.*`); `getHalftoneTokens`/`getHalftoneSourceMode`/`getHalftonePlacement`/`getHalftoneSceneOptions`/`getHalftoneInflateOptions` map those values onto the engine's `Tokens`/options shapes. `computeHalftoneRenderPlan` derives `cols`/`rows` from `state.canvas.size` + `grid.cellWidth`/`grid.cellAspect`, builds the `Field` via `buildHalftoneField`, and both the live preview and PNG export call this same function so they render identically. Uploaded media comes from `state.mediaAssets` (target `source.image`); rotate/flip transforms are baked into an offscreen canvas before being handed to the unmodified engine functions.

Where a control's real effect is on the exported file rather than the live preview (`export.image.format`, `export.image.resolution` -- confirmed via `rendererPipeline.interactionInvalidation`, which declares these two `mustNotInvalidate: build-field/build-ramp/rasterize-glyphs`), assert on the exported artifact's real decoded bytes (PNG/JPEG signature, decoded width) instead of a canvas-output diff, and excluded them from the generic canvas-diff test loop via a new `skipsCanvasOutputTest` catalog flag so that structurally-impossible assertion is not left permanently red in the suite. Several real defects were found and fixed along the way rather than worked around: (1) `appearance.ink`/`appearance.background` never reached the engine at all -- Toolcraft's `color` control commits edits as `{ hex: string }`, not a plain string, but `halftone-tokens.ts` only accepted `typeof value === "string"`, so every edit silently kept the hardcoded default; fixed with a `colorHex()` reader handling both shapes. (2) The shared slider-drag test helper could silently no-op when a control's default value's own ratio matched the hardcoded "primary" drag ratio (e.g. `character.variety`); fixed with a same-position retry from the opposite end of the track. (3) `character.size`'s schema range (ported as-is from the reference dial config) exceeds `halftone-draw.ts`'s real `[0.05, 1]` fill clamp, and the Regular/Medium/Light font weights render byte-identical in the available monospace stack (only Bold is visually distinct); both are faithful-to-reference behavior, not bugs, so the catalog's drag ratio / primary option were adjusted to values that are actually distinguishable. (4) `tone.backgroundCutoff` has no effect in Scene/Silhouette mode (`drawHalftone` only applies it when the field has no depth), so its test needed Image mode and a full-range gradient fixture, not the default state.

## Decisions

### Renderer

- Decision: Canvas 2D, reusing the reference engine's `drawHalftone` (glyph `fillText` drawing) unchanged; product code only supplies the field/tokens and composes the result into Toolcraft's canvas/export surfaces.
- Reason: The reference algorithm draws real monospace glyphs via `ctx.font`/`ctx.fillText`, not a per-pixel shader/filter; `productRepresentation: "text"` matches `rendererWorkload: "text-output"`, so no GPU-alternative evidence is structurally required. Rewriting to WebGL/WebGPU would replace the reference technique the user asked to keep as-is.
- Evidence: `src/app/halftone.ts` (unchanged engine), `src/app/halftone-canvas.tsx`, `src/app/halftone-export.ts`, `src/app/app-performance.ts` `rendererTechnique`/`rendererPipeline`.
- Known limitation: `app-performance.renderer-source.test.ts`'s `sourceUsesCpuPixelLoop()` check does a source-wide regex for `getImageData`/`putImageData`/`createImageData` and, if found anywhere, requires `rendererWorkload: "pixel-output"` and a WebGL/WebGPU strategy. The reference engine's `readKeyField`/`fieldFromImage` legitimately call `getImageData` once per source change to sample an uploaded image into the per-cell field (bounded to at most a ~600x600 supersampled key field); that is not the per-frame rendering technique, which remains Canvas 2D `fillText` glyph drawing. This is a known false-positive in that generated test's heuristic, not a reclassification of the app's real renderer; reclassifying to `pixel-output`/WebGL to satisfy the regex would misrepresent the actual architecture. See the top-level Risks section.

### Timeline

- Decision: No timeline (`panels.timeline` omitted); `animationIntent.mode: "none"`.
- Reason: This pass ships static scene/image sources only. Video-as-source (the one feature that would need transport) was explicitly deferred to a follow-up pass per an explicit scoping decision during this migration.
- Evidence: `src/app/app-schema.ts` (`panels.timeline` absent), `src/app/app-acceptance-data.ts` `appTransferMode.animationIntent`/`referenceTimeline`.

### Layers

- Decision: No layers (`panels.layers` omitted).
- Reason: The app edits one output surface (a single uploaded image feeding one renderer); there is no multi-object, multi-layer workflow.
- Evidence: `src/app/app-schema.ts` (`panels.layers` absent).

### Controls

- Decision: Group controls into Source, Placement, Silhouette, Character, Grid, Tone, Light, and Ink sections, plus the required Background and Image Export sections.
- Reason: Each section maps to one product/workflow entity from the reference app (source selection, media placement, silhouette shading, glyph ramp, grid sizing, tone mapping, lighting, ink color); dependent controls (e.g. Placement, Silhouette, Light) use `visibleWhen` against `source.mode` instead of always-visible dead controls.
- Evidence: `src/app/app-schema.ts`; `src/app/app-acceptance-data.ts` `appControlSectionInventory`.
- Known limitation: the Ink and Silhouette sections each trigger a layout/entity-grouping validator finding; deliberately not restructured this pass. See the top-level Risks section.

### Export

- Decision: Still-image product; sticky `panelActions` expose Export PNG (`role: "export-image"`) and Copy Tokens (`role: "copy-output"`); no video export since there is no timeline.
- Reason: No animated output exists in this pass, so `Export Video` does not apply; Copy Tokens ports the reference app's "Copy tokens JSON" feature used to generate production assets offline.
- Evidence: `src/app/app-schema.ts` (Export section), `src/app/halftone-export.ts` (`exportHalftonePng`, `copyHalftoneTokens`), `src/app/app-composition.tsx` (`onPanelAction`).

## Risks

Four known items remain open. None are new defects; each is either a pre-existing environment/framework false positive or a deliberately deferred product decision.

- Risk: pre-existing, environment-specific, not a product defect. A Windows-only path-separator mismatch in `app-acceptance.framework-boundary.test.ts` reproduces on a clean checkout before any product change (backslash vs. forward-slash path comparison in the framework's own resolver test). Accepted as a known environment difference; not touched.
- Risk: pre-existing, known framework heuristic false positive. `app-performance.renderer-source.test.ts`'s `sourceUsesCpuPixelLoop()` heuristic misclassifies the renderer because it flags any `getImageData` call anywhere in product source, including the reference engine's legitimate one-time image-sampling calls in `readKeyField`/`fieldFromImage`. The real per-frame rendering technique remains Canvas 2D `fillText` glyph drawing (see the Renderer decision's "Known limitation" note); reclassifying to `pixel-output`/WebGL to satisfy the regex would misrepresent the actual architecture. Accepted; not touched.
- Risk: deliberately deferred, tracked. `getToolcraftSeparatedColorPlacementErrors` in `src/app/acceptance/control-layout-entity-rules.ts` (the `controls-component-layout-invariants` contract rule) reports `Ink / ink is separated from other "appearance" controls...`. The Ink section (`appearance.ink` only) is a color-only section sharing the `appearance.*` target prefix with the separate, required Background section (`appearance.background` + `export.includeBackground`); this specific rule has no `splitReason`/`workflowStage` evidence override (unlike the sibling `getToolcraftProductEntitySplitErrors` check), so it reports unconditionally whenever a color-only section and another section share a loose prefix, regardless of documented intent. Confirmed via `git stash` to already be present at the last committed baseline before the acceptance-row work began. Two candidate resolutions, deliberately not applied: (1) merge `appearance.ink` into the Background section, so one section owns every `appearance.*` target (removes the split, but changes the reference product's Ink/Background section grouping); or (2) move `appearance.ink` onto a differently-prefixed target so Ink and Background no longer share a loose prefix, without changing section membership (more invasive: touches `halftone-tokens.ts`, `halftone-control-catalog.ts`, and every test/acceptance reference to `appearance.ink`). Deferred to a deliberate decision when the Background section's layout is revisited, not a forced merge under validator pressure.
- Risk: deliberately deferred, tracked, pre-existing. The Silhouette section's `invert`/`showMask` toggle controls trigger the `controls-component-layout-invariants` adjacent-short-toggle heuristic, which recommends a two-column inline `layoutGroup`. Confirmed present at the last committed baseline via `git stash`, unrelated to the acceptance-row work. Deliberately not restructured this pass; a real fix is a small, low-risk `layoutGroups` schema addition, deferred alongside the Ink/Background decision above so both layout changes are reviewed together.
